# Project Instructions

## Documentation order

The README and architecture documentation must explain the practical application and benefit in plain, nearly layman's language before introducing technical architecture, schemas, code, or implementation details.

Preserve that order when revising either document:

1. What problem does this solve for an ordinary buyer, seller, or operator?
2. What practical benefit does it create?
3. What does a realistic result look like?
4. Only then explain how the system works technically.

Do not replace the opening explanation with AI, data, architecture, or product-management jargon. Technical precision belongs in the later sections.

## Evidence boundaries

- Keep all public examples synthetic unless properly licensed public data is intentionally added.
- Keep hard constraints separate from weighted scoring.
- Do not allow generated language to override failed constraints or missing evidence.
- Preserve make, model, and model-number identity.
- Preserve source, date, version, and confidence information.
- Keep recommendation, human approval, quote, sale, deployment, and observed outcome distinct.
